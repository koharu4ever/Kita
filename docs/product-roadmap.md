# Kita 产品方向与维护原则

> 最后核对：2026-09-02
>
> 本文维护稳定的范围和取舍；完成度、验证证据和待处理边界只维护在 [当前项目状态](./current-project-status.md)。

## 产品定位

Kita 是具有视觉小说氛围的自托管游戏目录与长篇评论网站：

- Home 提供氛围和导航；
- Games 作为视觉馆藏和资料入口；
- Reviews 承载独立文章与阅读体验，Giscus 提供外部评论；
- Tools 组织个人工具箱；
- About 介绍项目及其实现。

站主通过 Payload Admin 编辑内容；访客浏览公开内容。Next.js、Payload、PostgreSQL 与 R2 构成一个职责明确的单体应用，不以增加服务数量作为成长目标。

## 保留的设计取舍

- Payload 提供内容与认证基础，应用负责内容规则和公开体验，不再叠加第二套 API 框架或 ORM。
- Games 使用 Media relationship；Review 可独立存在。只有真实内容要求“一篇 Review 必属一个 Game”时，才考虑关联迁移。
- 使用 Giscus/GitHub Discussions，不自建评论存储、登录和审核系统。
- 视觉效果是渐进增强；导航、阅读与键盘操作不应依赖持续动画、声音或 WebGL 成功。
- 开发 preview 与正式数据隔离；不通过生产 fixture、静态 fallback 或公开 seed route 撑满页面。

## 内容维护

公开条目应有明确用途，保持可读正文、准确日期和有效的官方/参考链接。图片、音频和其他素材需有清楚的来源及公开使用边界，不提供未经确认授权的商业内容下载。

Repository 资源归属只记录在 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)；生产内容由站主在 Payload 中维护。静态文件替换不会自动覆盖 R2 对象，数据库备份也不会自动备份图片本体。

## 接受新工作的条件

优先顺序为：

1. 数据安全、认证、部署或恢复问题；
2. 阻止内容发布、访问和正常阅读的缺陷；
3. 可访问性、浏览器兼容性和已有功能的回归；
4. 能让现有行为更容易验证或维护的小型测试、文档改进；
5. 有真实使用需求且维护收益明确的新能力。

每项工作应有单一目标、明确验收和可回滚边界。没有新需求时保持维护状态，不把历史路线图自动当作下一轮开发授权。

## 暂不引入

- 多人编辑角色、Payload drafts/versions、Trash，除非编辑流程出现实际需求；
- 公共注册、自建评论、独立搜索平台；
- Redis、第二套 ORM、微服务、Kubernetes；
- OpenList 深度集成或共享用户系统；
- 大型监控平台和全量跨浏览器视觉回归矩阵。

展示材料使用真实页面，不用 mock 截图冒充上线状态；功能、测试与运维能力分别依据代码、检查结果和演练证据描述，不用“已上线”代替全部验收。
